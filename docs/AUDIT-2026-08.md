## 2. 발견 → 수정

| # | 발견 | 어떤 시나리오에서 터지나 | 어떻게 고쳤나 |
|---|---|---|---|
| **H1** | **결제 리플라이의 `paymentId` 유실.** `processed_commands`는 커맨드가 중복 도착했을 때 "이미 처리했다"는 사실만 기억하고, 그 결과였던 `paymentId`는 저장하지 않았다. | `SagaTimeoutSweeper`가 응답이 늦다고 판단해 `ChargePayment` 커맨드를 **재전송**한다 → payment-service는 이미 처리한 커맨드임을 알아채고 **저장된 결과로 리플라이를 재생**하지만, `paymentId`가 없으니 **`null`로 응답**한다 → order의 `Order.confirm(null)`이 (당시엔) 예외를 던지거나 조용히 실패해 확정에 실패한다 → 조정자는 계속 실패로 보고 다시 재촉하다 결국 **`giveUp`으로 Saga를 종료**한다 → 하지만 결제는 이미 **실제로 청구된 상태**라 고아 결제가 남는데, 정상 리플라이 경로가 막혀 있었으므로 Phase 14의 고아 결제 보상 경로(§PHASE-14 §4.8)도 올바른 `paymentId`를 받지 못해 **"청구는 됐는데 확정도 환불도 안 되는"** 상태에 빠질 수 있었다. | `processed_commands`에 `payment_id` 컬럼 추가(`payment` V5·`inventory` V5·`order` V9 마이그레이션). `PaymentCommandService`가 중복 커맨드의 리플라이를 재전송할 때 **저장해 둔 `paymentId`를 그대로 실어 보낸다**. 방어적으로 `Order.confirm(null)`도 예외 대신 **`false`를 반환**하도록 정리(다른 멱등 가드들과 일관된 방식). 테스트 단언 추가. |
| **H2** | **코레오그래피 순서 역전 시 주문 영구 미확정.** `Order.confirm`이 `INVENTORY_RESERVED`에서만 확정을 허용했다. | 코레오그래피 모드에서 `InventoryReserved`와 `PaymentCharged`는 **서로 다른 리스너 컨테이너**가 처리하므로 도착 순서가 보장되지 않는다. `PaymentCharged`가 먼저 도착하면 그 시점 주문은 아직 `PENDING`이라 확정 지시가 조용히 무시되고, 뒤늦게 `InventoryReserved`가 와도 이미 지나간 `PaymentCharged`는 다시 오지 않으므로 주문은 **"결제됐는데 영영 미확정"**으로 남는다. | `Order.confirm`을 **단조(monotonic) 전이**로 변경 — `PENDING`에서도 `PaymentCharged`를 받아들인다(읽기 모델 `OrderViewStatus.rank`와 같은 원리). 늦게 온 `InventoryReserved`는 `markInventoryReserved`가 (이미 `PENDING`이 아니므로) 무시한다. → [PHASE-12-SAGA.md](PHASE-12-SAGA.md) §4.1·§4.9. |
| **IDOR** | **인가 경로 2건.** ① 게이트웨이에 `payments-route`가 살아 있어, 인증만 된 사용자면 `POST /payments`를 직접 호출해 Saga·멱등성·보상을 전부 우회할 수 있었다. ② `POST /orders`의 `customerId`를 클라이언트가 요청 본문으로 지정할 수 있어 남의 이름으로 주문을 만들 수 있었고, `GET /orders/{id}`에도 소유권 검사가 없어 아무 인증 사용자나 남의 주문을 조회할 수 있었다. | 유효한 JWT만 있으면(역할 무관) 임의 결제 생성 또는 타인 주문 열람/생성이 가능한 상태 — 전형적 IDOR(A01: Broken Access Control). | 게이트웨이 `payments-route` **삭제**(결제는 Saga/Kafka 커맨드로만 구동 — payment-service 자체 JWT 검증은 유지, defense in depth). `POST /orders`의 `customerId`는 **요청 몸통이 아니라 JWT subject에서 유도**(`CustomerIds.fromSubject` — 이름 기반 UUID(v3), 몸통의 `customerId`는 무시 — 기존 스크립트 호환 유지). `GET /orders/{id}`는 **본인 또는 ADMIN만** 허용(아니면 403 `AccessDeniedException`). |
| **CI** | **CI 워크플로 토큰 권한이 저장소 기본값에 의존.** | `permissions`를 명시하지 않은 잡은 저장소 설정의 기본 `GITHUB_TOKEN` 권한(때로 read/write)을 상속한다. `./gradlew build`가 실행하는 서드파티 코드(Gradle 플러그인·Testcontainers)가 이론상 `main`에 push할 수 있는 경로가 열려 있었고, Argo CD의 `selfHeal`이 `main`을 그대로 신뢰하므로 이는 곧 클러스터 장악 경로로 이어질 수 있었다. | 워크플로 최상단에 `permissions: contents: read` 추가(기본값을 읽기 전용으로 못 박음). push하지 않는 잡의 checkout에 `persist-credentials: false` 추가(그 잡 안에서 git 자격증명이 애초에 남지 않게). |
| **Grafana** | **Grafana 익명 접근이 Admin 권한.** | k8s(`deploy/k8s/base/otel-lgtm.yaml`)의 `GF_AUTH_ANONYMOUS_ORG_ROLE`이 `Admin`이라, Ingress로 노출되면 로그인 없이 누구나 대시보드·데이터소스 설정을 바꿀 수 있었다. | k8s의 익명 역할을 `Admin` → **`Viewer`**로 낮춤(`base/otel-lgtm.yaml`). ⚠️ compose(`deploy/compose/compose.yml`)는 로컬 전용이라 범위 밖으로 두고 `Admin`을 유지했다 — 필요하면 별도로 낮출 것. |

## 4. 보안 스캔 결론 (공개 저장소)

이 저장소는 `github.com/jyh4358/msa-practice`로 **공개**돼 있어, 전체 커밋 이력을 별도로 스캔했습니다.

- **실 자격증명·PII: 전체 이력에서 0건.** DB 비밀번호·RSA 키 등은 전부 학습용 dev 값이며 실서비스 자격증명이 아니다.
- **`.secrets/`·`.env` 커밋 이력: 0건.** 둘 다 처음부터 `.gitignore` 대상이었고, 이력을 뒤져도 실수로 커밋된 적이 없다.
- 커밋 author/committer 이메일의 오타(`gamil.com`)를 `git filter-repo --mailmap`으로 정정 — 이건 민감정보가 아니라 **기여 그래프 연결**(GitHub이 커밋을 계정에 매칭) 목적의 이력 재작성이었다(→ [PHASE-COMMIT-MAP.md](PHASE-COMMIT-MAP.md) 상단 경고 참고).

> **교훈: "비밀이 커밋되면 리라이트가 아니라 로테이션."** 이번 재작성은 민감정보 제거가 목적이 아니었지만, 만약 그랬다면
> `git filter-repo`로 이력에서 지우는 것만으로는 부족하다 — 그 커밋을 참조하는 포크·클론·이미 받아 간 `git fetch`가 있다면
> "고아 커밋"은 **GitHub 서버 쪽에도 한동안 남는다**(reflog·GC 유예기간). 유출된 비밀의 유일하게 확실한 대응은
> **그 비밀 자체를 무효화(로테이션)**하는 것이다 — 이력 재작성은 위생 조치일 뿐, 보안 조치가 아니다.

## 5. API 변화 요지

이번 감사로 바뀐 외부 API 동작(§2 IDOR 항목의 결과):

- **`POST /orders`의 `customerId` 몸통 필드는 이제 무시된다.** 실제 고객 id는 항상 **JWT subject에서 유도**된다
  (`CustomerIds.fromSubject`). 요청 본문에 `customerId`를 넣어도 무해하게 무시되므로 기존 클라이언트/스크립트는
  그대로 동작한다(하위 호환 유지) — 다만 그 값이 **더 이상 신뢰되지 않는다**는 점은 통합 대상이라면 알아 둬야 한다.
- **`GET /orders/{id}`가 403을 반환할 수 있다.** 요청자가 그 주문의 소유자가 아니고 ADMIN도 아니면
  `AccessDeniedException` → 403. 이전에는 인증만 됐으면 아무 주문이나 조회할 수 있었다.
- **게이트웨이에서 `/payments` 라우트가 사라졌다.** `POST :8000/payments`(또는 `/payments/**`)는 더 이상
  게이트웨이를 통해 도달할 수 없다(404 또는 라우트 없음). 결제는 오직 Saga(Kafka 커맨드)로만 일어난다.
  payment-service를 클러스터/컴포즈 내부에서 직접 호출하는 것은 여전히 가능하지만(그 경로엔 자체 JWT 검증이 있다),
  공개 게이트웨이로는 노출되지 않는다.
