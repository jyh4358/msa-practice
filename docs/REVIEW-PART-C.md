## 1. 큰 그림 — 두 가지 Saga 를 **둘 다** 만들었다

이 프로젝트의 특이한 점: Saga 를 **한 가지만 고르지 않고 둘 다 구현**하고 `saga.mode` 로 토글합니다.
같은 문제를 두 방식으로 풀어 봐야 트레이드오프가 몸에 남기 때문입니다. **상호배타**입니다(동시에 켜면 이중 처리).

```
◆ choreography (Phase 12) — 조정자가 없다
    order ──OrderPlaced──▶ inventory ──StockReserved──▶ payment
                                │                          │
                          StockRejected              PaymentApproved / PaymentRejected
                                │                          │
                                ▼                          ▼
                          order 가 듣고 CANCELLED    order 가 듣고 CONFIRMED / 보상 시작
    · 각자 "남의 사실"을 듣고 스스로 반응
    · 장점: 결합 낮음, 서비스 추가가 쉬움
    · 단점: 전체 흐름이 어디에도 안 적혀 있다 (코드를 다 읽어야 안다)

◆ orchestration (Phase 13, 기본값) — order 가 조정자
                    ┌──────────── order (조정자) ────────────┐
                    │  saga_instance 테이블 = 상태기계         │
                    │  STARTED → AWAITING_INVENTORY →        │
                    │  AWAITING_PAYMENT → COMPLETED          │
                    │  실패 시 COMPENSATING_INVENTORY → CANCELLED │
                    └──┬──────────────────────────▲──────────┘
        saga-commands  │                          │  saga-replies
         (지시)         ▼                          │   (결과)
                inventory / payment ──────────────┘
    · 장점: 흐름이 한 곳(switch 하나)에 다 있다, 타임아웃 처리 가능
    · 단점: 조정자가 중심점이자 단일 장애점, 서비스 추가 시 조정자를 고쳐야 함
```

**핵심 한 문장:** 분산 환경에는 롤백이 없으므로 **되돌리는 일을 직접 짠다**(보상).
그리고 그 일련의 과정을 **어디에 적어 둘 것인가**(각자 vs 한 곳)가 코레오그래피와 오케스트레이션의 차이다.

## 2. 단계별 회고 (무엇을·왜)

| Phase | 무엇을 | 왜(어떤 문제를 풀려고) |
|---|---|---|
| **12** Saga(코레오그래피) | 동기 결제 호출 **삭제**, 주문 상태기계, **보상**(재고 해제), outbox 에 `traceparent` 저장·복원 | Phase 2 이후 열려 있던 **분산 트랜잭션 부재**를 처음으로 정면 대응 |
| **13** Saga(오케스트레이션) | 중앙 조정자 + `saga_instance` + **`SagaTimeoutSweeper`** + **결정적 커맨드 키** | 코레오그래피는 **아무도 응답을 안 하면 영원히 멈춘다**(타임아웃 주체가 없음) |
| **14** 복원력 | Resilience4j 5종, 게이트웨이 회로차단기+fallback, 엣지 RateLimiter/Bulkhead, **DLQ**, outbox 격리, **고아 결제 환불 보상** | "실패는 일어난다" — 전파를 끊고, 독을 격리하고, 못 되돌린 것을 뒤늦게라도 보상 |
| **15** 계약·설정 방송 | Spring Cloud Bus, **계약 테스트**(동기 API + 이벤트), tolerant reader | 서비스가 늘자 **"내가 바꾸면 누가 깨지나"** 를 알 수 없게 됨 |

> **관통하는 실:** Phase 2 → 10 → 12/13 이 하나의 이야기다.
> **깨졌다 → 배관을 놨다 → 되돌리기를 짰다.** 그리고 14 가 "그 배관도 고장 난다"를 다룬다.

## 4. 셀프 퀴즈 (답은 아래 접힘)

1. 재고는 예약됐는데 결제가 거절됐다. 데이터베이스 롤백으로 되돌릴 수 있나? 그럼 어떻게 되돌리나?
2. 코레오그래피 모드에서 **payment 서비스가 통째로 죽어** 아무 응답도 안 하면 그 주문은 어떻게 되나?
3. 오케스트레이션의 `SagaTimeoutSweeper` 가 15초 무응답에 커맨드를 **재전송**한다. 이때 결제가 **두 번 청구**될 위험이 있다. 왜 `processed_messages`(메시지 id 기반) 로는 못 막나?
4. 3번의 답으로 도입한 `processed_commands` 에서, 중복 커맨드를 발견하면 **그냥 무시**하면 어떻게 되나?
5. 게이트웨이 회로차단기가 OPEN 되면 사용자는 무엇을 받나? 그게 왜 "그냥 500" 보다 나은가?
6. 재시도를 켰는데 오히려 장애가 커졌다. 어떤 상황일까?
7. 어떤 메시지가 역직렬화에서 계속 실패한다. 이걸 방치하면 무슨 일이 생기나? DLQ 는 그걸 어떻게 막나?
8. 고아 결제(orphan payment)란 무엇이고, 왜 Saga 만으로는 안 잡혔나?
9. `OrderPlacedEvent` 에 필드를 **추가**하는 건 안전하다고 했다. 왜? 반대로 **제거**하면 무엇이 깨지나?
10. `config-repo` 값을 바꾸고 order-service **한 대**에만 `/actuator/busrefresh` 를 쳤다. 나머지 인스턴스는?

<details><summary>정답 펼치기</summary>

1. **롤백은 불가능하다.** 재고 예약은 **이미 커밋된 다른 서비스의 트랜잭션**이다. 되돌리려면 "예약을 해제한다"는 **새 트랜잭션(보상)** 을 실행해야 한다. 그래서 보상은 "없던 일로"가 아니라 **"반대 방향의 사실을 하나 더 만드는 일"** 이다.
2. **영원히 `PENDING` 에 머문다.** 코레오그래피에는 **전체 흐름을 감시하는 주체가 없어서** 타임아웃을 걸 자리가 없다. 이게 Phase 13(오케스트레이션)을 만든 직접적 이유다.
3. **재전송할 때 메시지 id 가 새로 생기기 때문이다.** 소비자는 "처음 보는 메시지"로 판단해 정상 처리한다. 즉 메시지 기반 dedup 은 **같은 메시지의 재전달**은 막지만 **같은 의도의 새 메시지**는 못 막는다. 그래서 `sagaId + 커맨드 타입` 으로 **의도 자체를 키로** 삼는 결정적 키가 필요하다.
4. **조정자가 영영 기다린다.** 중복이라고 판단해 조용히 무시하면 리플라이가 안 가고, 조정자는 응답을 못 받아 또 재촉하고… 무한 루프다. 올바른 처리는 **저장해 둔 결과로 리플라이를 다시 보내는 것**이다.
5. **fallback 응답**(예: "일시적으로 처리할 수 없습니다")을 받는다. 나은 이유는 ① 사용자에게 **빠르게** 응답하고(타임아웃까지 안 기다림) ② 죽어가는 서비스에 **부하를 더 얹지 않아** 회복할 틈을 준다.
6. **재시도 폭풍.** 다운스트림이 과부하로 느려진 상황에서 모든 클라이언트가 재시도하면 **부하가 배로** 늘어 더 죽는다. 그래서 재시도는 회로차단기·지수 백오프·지터와 **같이** 써야 하고, 멱등하지 않은 연산에는 아예 쓰면 안 된다.
7. **컨슈머가 그 오프셋에서 멈춰 그 파티션의 뒤쪽 메시지가 전부 막힌다**(head-of-line blocking). DLQ 는 N 회 실패한 메시지를 `.DLT` 토픽으로 **옆으로 치우고** 오프셋을 전진시켜 나머지가 흐르게 한다. 치운 건 나중에 사람이 보고 고쳐서 재투입한다.
8. **결제는 승인됐는데 그 사실이 order 에 반영되지 못한 상태.** 예컨대 리플라이 유실이나 조정자 타임아웃 포기 시점이 어긋나면 생긴다. Saga 상태기계는 "내가 아는 상태"만 되돌리므로, **조정자가 모르는 결제**는 보상 대상에 안 들어간다. Phase 14 는 `RefundPaymentCommand` 로 **뒤늦게 환불**하는 경로를 따로 만들었다.
9. **tolerant reader** 규칙 때문이다. 소비자는 모르는 필드를 무시하도록 역직렬화를 설정했으므로, 추가는 옛 소비자에게 **보이지 않을 뿐** 깨지지 않는다. 반대로 제거·개명은 **그 필드를 읽던 소비자가 즉시 깨진다**(null 또는 역직렬화 실패). 그래서 제거는 "아무도 안 읽는다"를 확인한 뒤 여러 릴리스에 걸쳐 한다.
10. **전부 반영된다.** Bus 가 그 리프레시 요청을 **Kafka 토픽으로 방송**하고, 같은 Bus 에 붙은 모든 인스턴스가 그걸 듣고 각자 리프레시한다. 단 **`@Value` 로 주입한 값은 안 바뀐다** — `@ConfigurationProperties` 여야 재바인딩된다.

</details>

## 5. 재현 체크리스트

- [ ] `--profile async` 로 전체 기동 후 **정상 주문** → `CONFIRMED` 까지 확인.
- [ ] ★ **실패 경로**: 합계가 `.99` 로 끝나는 주문을 넣어 결제 거절 → **재고가 해제되고** `CANCELLED` 되는지 확인.
      `SELECT * FROM stock_reservations;` 로 예약 원장이 되돌아가는지 눈으로.
- [ ] `SELECT state FROM saga_instance WHERE order_id='…';` 로 상태 전이를 추적.
- [ ] ★ **타임아웃**: inventory 를 내리고 주문 → `SagaTimeoutSweeper` 가 재촉하다 포기하는지 로그로 확인.
- [ ] ★ **모드 토글**: `saga.mode` 를 `choreography` 로 바꿔 재기동 → 같은 주문이 **다른 경로로** 완주하는지 확인. (⚠️ 둘을 동시에 켜지 말 것)
- [ ] **회로차단기**: `ChaosController` 로 inventory 를 고장 내고 게이트웨이가 fallback 을 주는지 확인.
- [ ] **DLQ**: 잘못된 형식의 메시지를 토픽에 넣고 `.DLT` 로 가는지 kafka-ui 에서 확인.
- [ ] **계약 테스트**: `inventory-service` 의 계약을 일부러 깨뜨리고 `order-service` 빌드가 **실패**하는지 확인. ★ 이게 계약 테스트의 존재 이유.
- [ ] **Bus**: 설정을 바꾸고 한 인스턴스에 `busrefresh` → 다른 인스턴스에도 반영되는지.
- [ ] 각 단계에서 "왜 이 장치가 필요한가"를 스스로 설명.
