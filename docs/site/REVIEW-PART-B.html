2차 복습 — 파트 B: 관측성 먼저, 그 다음 비동기 (Phase 8~11)

⚠️ 이 복습은 Phase 8~11 시점을 다룹니다. 이후 크게 바뀐 것 둘: Phase 12 에서 order→payment 동기 REST 가 완전히 사라지고 Kafka 이벤트 Saga 가 됐고, Phase 16b 에서 Config Server 가 삭제돼 설정이 deploy/config/ 파일로 옮겨갔습니다. (그래서 아래에 config-repo 가 나오면 "지금은 deploy/config/" 로 읽으세요.)

파트 A 가 동기 플랫폼을 세웠다면, 파트 B 는 그 위에 눈(관측성) 을 달고 결합을 끊는(비동기) 단계입니다. 순서가 중요합니다 — 비동기로 가면 흐름이 눈에 안 보이므로 관측성을 먼저 깔았습니다. 큰 그림 → 단계 회고 → 개념 자가진단 → 셀프 퀴즈 → 재현 체크리스트 → 아직 열린 한계 순.

1. 큰 그림 — 파트 B 가 끝났을 때의 모양

                        클라이언트
                            ▼
                   gateway (8000)
                       │
          ┌────────────┼─────────────────┐
          ▼            ▼                 ▼
   order (8080)   payment (8081)   order-query (8083)  ← 읽기 전용
      │  │                                  ▲
      │  └─ 동기 REST ─▶ payment            │ 투영
      │                                      │
      ▼ ① 같은 트랜잭션에 INSERT              │
   ┌─────────────┐                           │
   │ orderdb     │                           │
   │  orders     │                           │
   │  outbox ────┼─② @Scheduled 릴레이 ─┐    │
   └─────────────┘                      │    │
                                        ▼    │
                              ┌──────────────┴───┐
                              │  Kafka           │
                              │  order-events    │
                              └──┬───────────────┘
                                 │ ③ 소비 (messageId 로 멱등)
                                 ▼
                          inventory (8082) ── inventorydb
                                              processed_messages

   ─────────────────────────────────────────────────────────────
   관측성:  모든 서비스 ──OTLP──▶ otel-lgtm (Tempo·Loki·Prometheus·Grafana:3000)
            trace 가 gateway→order→[Kafka]→inventory 까지 '하나로' 이어진다

핵심 한 문장: 쓰기는 DB 한 번만 하고(outbox), 발행은 나중에 따로(릴레이), 소비는 중복돼도 안전하게(멱등) 만든 다음, 읽기는 따로 만든 모델(CQRS)에서 가져온다. 그리고 그 전 과정이 한 트레이스로 보인다.

2. 단계별 회고 (무엇을·왜)

Phase 무엇을 왜(어떤 문제를 풀려고)
8a 트레이싱·메트릭 Micrometer Tracing + OTLP → otel-lgtm. trace/span, traceparent 전파 서비스가 여럿이 되자 "이 요청이 어디서 느렸나"를 알 수 없게 됨
8b 로그·대시보드 로그 → Loki, RED 대시보드, 트레이스↔로그 상호 점프 로그가 서비스별로 흩어져 한 요청을 따라갈 수 없음
9a 비동기 inventory 분리, OrderPlaced 이벤트 발행/소비, HTTP→Kafka 트레이스 전파 동기 호출은 장애가 전파되고 같이 느려짐(시간적 결합)
10 Outbox+멱등 트랜잭셔널 outbox + @Scheduled 릴레이 + processed_messages 이중 쓰기 문제 — DB 커밋과 Kafka 발행이 원자적이지 않음
11 CQRS order-query-service + MongoDB 읽기 모델, 이벤트 투영 조회가 쓰기 모델을 침범(조인 폭발·성능·모델 오염)

관통하는 실: Phase 2 에서 생긴 "분산 트랜잭션이 사라졌다" 는 문제를 파트 B 는 정면으로 풀지 않는다. 대신 신뢰할 수 있는 메시지 전달(outbox+멱등)이라는 척추를 먼저 세운다. 그 위에서 파트 C 의 Saga 가 가능해진다.

4. 셀프 퀴즈 (답은 아래 접힘)

  1. orders INSERT 와 Kafka send() 를 하나의 @Transactional 안에 넣으면 무엇이 잘못되나? 실패 조합 두 가지를 말해보세요.
  2. Outbox 를 쓰면 "정확히 한 번(exactly-once)" 전달이 되나?
  3. 릴레이가 같은 outbox 행을 두 번 발행할 수 있나? 그래도 괜찮은 이유는?
  4. inventory 가 같은 OrderPlaced 를 두 번 받으면 재고가 두 번 깎이나? 막는 장치는?
  5. HTTP 요청에서 시작된 trace 가 Kafka 를 건너 inventory 까지 이어지려면 무엇이 필요한가? (outbox 가 끼어 있다는 점에 주의)
  6. 주문 직후 GET /order-views 에 그 주문이 안 보일 수 있다. 버그인가?
  7. Mongo 읽기 모델을 통째로 지우고 다시 만들 수 있나? 조건은?
  8. RestClient 로 부른 payment 호출이 Grafana 트레이스에서 span 이 안 보인다. 무엇을 빠뜨렸나?
  9. Kafka 컨슈머 그룹을 새로 만들고 auto-offset-reset: earliest 로 붙이면 무슨 일이 일어나나?
정답 펼치기
  1. Kafka 는 DB 트랜잭션에 참여하지 않는다. ① DB 커밋 성공 + 발행 실패 → 재고가 영원히 안 깎임(이벤트 유실). ② 발행 성공 + DB 롤백 → 있지도 않은 주문에 대해 재고가 깎임(유령 이벤트). 둘 다 조용히 일어난다.
  2. 아니다. outbox 는 at-least-once(최소 한 번)를 준다. 릴레이가 발행 후 published=true 로 표시하기 전에 죽으면 다시 발행한다. "정확히 한 번"처럼 보이게 만드는 건 소비자 쪽 멱등성이고, 그 합을 effectively-once 라고 부른다.
  3. 있다(2번의 그 창). 괜찮은 이유는 소비자가 messageId 로 중복을 걸러내기 때문 — processed_messages 에 이미 있으면 처리하지 않고 성공 처리한다.
  4. 아니다. processed_messages(message_id) 유니크 제약이 두 번째를 막는다. 중요한 건 "무시"가 아니라 같은 트랜잭션 안에서 기록해야 한다는 것(기록만 되고 처리가 롤백되면 영영 유실).
  5. traceparent 를 outbox 행에 같이 저장했다가 릴레이가 발행할 때 Kafka 헤더로 복원해야 한다. outbox 를 거치면서 원래 요청의 스레드/컨텍스트가 끊기기 때문. (Phase 12 에서 이걸 넣어 Saga 전체가 한 트레이스가 됐다.)
  6. 버그가 아니다. 쓰기(orders)와 읽기(order-views)가 이벤트로 연결돼 있어 결과적 일관성이다. UI 는 "처리 중"을 보여주거나, 방금 쓴 값은 쓰기 모델에서 읽는 식(read-your-writes)으로 다룬다.
  7. 가능하다. 조건은 투영이 결정적일 것 — 같은 이벤트 순서를 다시 먹이면 같은 결과가 나와야 한다. 투영 안에서 now()·랜덤·외부 호출을 쓰면 깨진다.
  8. ObservationRegistry. RestClient.Builder 를 스프링 자동설정 대신 직접 만들면 계측 인터셉터가 안 붙는다. 자동설정의 RestClientBuilderConfigurer 를 거치거나 registry 를 명시해야 한다.
  9. 그 그룹은 오프셋이 없으므로 토픽에 남아 있는 처음부터 전부 다시 읽는다. 이게 리플레이의 원리이고, 그래서 소비자가 멱등하지 않으면 재앙이 된다.

5. 재현 체크리스트 ("맨바닥에서 뜨면 체화된 것")

Phase 12 이후 구조에서 재현합니다. --profile async 가 필수입니다.

  • docker compose -f deploy/compose/compose.yml --profile async up -d → 13 컨테이너 healthy.
  • 주문 1건 넣고 Grafana(:8000/grafana) 에서 trace 하나를 열어 gateway→order→Kafka→inventory 가 이어지는지 확인.
  • 그 trace 에서 로그로 점프해 같은 요청의 로그가 보이는지 확인.
  • SELECT * FROM outbox ORDER BY id DESC LIMIT 5; — published 가 어떻게 변하는지 관찰.
  • Kafka 를 잠깐 내리고 주문을 넣어본다 → 주문은 성공(201), outbox 에 미발행으로 쌓임 → Kafka 를 올리면 저절로 흘러가는지 확인. ★ 이게 outbox 의 존재 이유다.
  • SELECT * FROM processed_messages; — 멱등 기록을 눈으로 확인.
  • 같은 이벤트를 일부러 두 번 흘려보내고 재고가 한 번만 깎이는지 확인.
  • GET /order-views?customerId=… 가 주문 직후엔 비어 있다가 잠시 뒤 채워지는 걸 관찰(결과적 일관성).
  • 각 단계에서 "왜 이 장치가 필요한가"를 스스로 설명.

한계 해결 Phase
분산 트랜잭션 정합성(고아 결제) — Phase 2 부터 아직도 열려 있음 Phase 12·13(Saga·보상)
실패했을 때 되돌리기가 없음(재고는 깎였는데 결제 실패하면?) Phase 12(보상 트랜잭션)

이벤트 스키마가 바뀌면 소비자가 깨짐(계약이 없음) Phase 15(계약 테스트·tolerant reader)
릴레이 폴링 지연(수백 ms~초) · DB 부하 Debezium CDC (미실시)
단일 호스트 · 이미지 수동 Phase 16(k8s)·17(CI/CD)

7. 다음 — 파트 C (Phase 12~15)

  • 12 Saga(코레오그래피): 동기 결제를 지우고, 각 서비스가 남의 사실 이벤트를 듣고 반응 + 보상.
  • 13 Saga(오케스트레이션): 중앙 조정자·상태기계·타임아웃 — 같은 문제의 다른 답을 비교.
  • 14 복원력: 회로차단기·격벽·재시도·DLQ — "실패는 일어난다"를 전제로.
  • 15 계약·설정 방송: 스키마 진화, Spring Cloud Contract.
