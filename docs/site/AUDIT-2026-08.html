감사 기록 — 2026-08-02

이 프로젝트는 각 Phase 문서 §8에 "알려진 한계"를 정직하게 적어 온 전통이 있습니다. 이 문서는 같은 정신으로, 완성 선언 이후에 진행한 감사에서 무엇을 발견했고 무엇을 고쳤는지(그리고 무엇을 안 고쳤는지) 남깁니다.

1. 감사 개요

날짜: 2026-08-02. 대상: Phase 019 전체(당시 "Phase 017 완료, Phase 18/19는 재번호매김 후 완료" 상태). 축 4개:

  1. 로드맵 정합성 — MSA-LEARNING-PLAN.md(계획)와 실제 구현·문서 사이의 어긋남(Phase 18 재번호매김, Keycloak→auth-service 직접구현, Config Server native+삭제 등).
  2. 구현(코드) 정합성 — Saga 상태기계·커맨드 리플라이 등 도메인 로직이 §8에 적힌 대로 실제로 방어되는지.
  3. 인프라 — k8s/Kustomize/GitOps 매니페스트, CI 워크플로의 하드닝 상태.
  4. 보안 — 인가 경로(IDOR 등)와 공개 저장소의 이력에 민감정보가 없는지.

이 문서는 ②·③·④에서 실제로 코드/설정을 고친 것(§2)과 ①·②·③에서 발견했지만 이번 라운드엔 고치지 않고 이연한 것(§3)을 정리합니다. 로드맵 정합성(①) 자체의 문서 정정은 MSA-LEARNING-PLAN.md 상단의 "실제 구축 결과" 주석과 BACKLOG.md로 반영했습니다.

2. 발견 → 수정

# 발견 어떤 시나리오에서 터지나 어떻게 고쳤나
H1 결제 리플라이의 paymentId 유실. processed_commands는 커맨드가 중복 도착했을 때 "이미 처리했다"는 사실만 기억하고, 그 결과였던 paymentId는 저장하지 않았다. SagaTimeoutSweeper가 응답이 늦다고 판단해 ChargePayment 커맨드를 재전송한다 → payment-service는 이미 처리한 커맨드임을 알아채고 저장된 결과로 리플라이를 재생하지만, paymentId가 없으니 null로 응답한다 → order의 Order.confirm(null)이 (당시엔) 예외를 던지거나 조용히 실패해 확정에 실패한다 → 조정자는 계속 실패로 보고 다시 재촉하다 결국 giveUp으로 Saga를 종료한다 → 하지만 결제는 이미 실제로 청구된 상태라 고아 결제가 남는데, 정상 리플라이 경로가 막혀 있었으므로 Phase 14의 고아 결제 보상 경로(§PHASE-14 §4.8)도 올바른 paymentId를 받지 못해 "청구는 됐는데 확정도 환불도 안 되는" 상태에 빠질 수 있었다. processed_commands에 payment_id 컬럼 추가(payment V5·inventory V5·order V9 마이그레이션). PaymentCommandService가 중복 커맨드의 리플라이를 재전송할 때 저장해 둔 paymentId를 그대로 실어 보낸다. 방어적으로 Order.confirm(null)도 예외 대신 false를 반환하도록 정리(다른 멱등 가드들과 일관된 방식). 테스트 단언 추가.
H2 코레오그래피 순서 역전 시 주문 영구 미확정. Order.confirm이 INVENTORY_RESERVED에서만 확정을 허용했다. 코레오그래피 모드에서 InventoryReserved와 PaymentCharged는 서로 다른 리스너 컨테이너가 처리하므로 도착 순서가 보장되지 않는다. PaymentCharged가 먼저 도착하면 그 시점 주문은 아직 PENDING이라 확정 지시가 조용히 무시되고, 뒤늦게 InventoryReserved가 와도 이미 지나간 PaymentCharged는 다시 오지 않으므로 주문은 **"결제됐는데 영영 미확정"**으로 남는다. Order.confirm을 단조(monotonic) 전이로 변경 — PENDING에서도 PaymentCharged를 받아들인다(읽기 모델 OrderViewStatus.rank와 같은 원리). 늦게 온 InventoryReserved는 markInventoryReserved가 (이미 PENDING이 아니므로) 무시한다. → PHASE-12-SAGA.md §4.1·§4.9.
IDOR 인가 경로 2건. ① 게이트웨이에 payments-route가 살아 있어, 인증만 된 사용자면 POST /payments를 직접 호출해 Saga·멱등성·보상을 전부 우회할 수 있었다. ② POST /orders의 customerId를 클라이언트가 요청 본문으로 지정할 수 있어 남의 이름으로 주문을 만들 수 있었고, GET /orders/{id}에도 소유권 검사가 없어 아무 인증 사용자나 남의 주문을 조회할 수 있었다. 유효한 JWT만 있으면(역할 무관) 임의 결제 생성 또는 타인 주문 열람/생성이 가능한 상태 — 전형적 IDOR(A01: Broken Access Control). 게이트웨이 payments-route 삭제(결제는 Saga/Kafka 커맨드로만 구동 — payment-service 자체 JWT 검증은 유지, defense in depth). POST /orders의 customerId는 요청 몸통이 아니라 JWT subject에서 유도(CustomerIds.fromSubject — 이름 기반 UUID(v3), 몸통의 customerId는 무시 — 기존 스크립트 호환 유지). GET /orders/{id}는 본인 또는 ADMIN만 허용(아니면 403 AccessDeniedException).
CI CI 워크플로 토큰 권한이 저장소 기본값에 의존. permissions를 명시하지 않은 잡은 저장소 설정의 기본 GITHUB_TOKEN 권한(때로 read/write)을 상속한다. ./gradlew build가 실행하는 서드파티 코드(Gradle 플러그인·Testcontainers)가 이론상 main에 push할 수 있는 경로가 열려 있었고, Argo CD의 selfHeal이 main을 그대로 신뢰하므로 이는 곧 클러스터 장악 경로로 이어질 수 있었다. 워크플로 최상단에 permissions: contents: read 추가(기본값을 읽기 전용으로 못 박음). push하지 않는 잡의 checkout에 persist-credentials: false 추가(그 잡 안에서 git 자격증명이 애초에 남지 않게).
Grafana Grafana 익명 접근이 Admin 권한. k8s(deploy/k8s/base/otel-lgtm.yaml)의 GF_AUTH_ANONYMOUS_ORG_ROLE이 Admin이라, Ingress로 노출되면 로그인 없이 누구나 대시보드·데이터소스 설정을 바꿀 수 있었다. k8s의 익명 역할을 Admin → **Viewer**로 낮춤(base/otel-lgtm.yaml). ⚠️ compose(deploy/compose/compose.yml)는 로컬 전용이라 범위 밖으로 두고 Admin을 유지했다 — 필요하면 별도로 낮출 것.

4. 보안 스캔 결론 (공개 저장소)

이 저장소는 github.com/jyh4358/msa-practice로 공개돼 있어, 전체 커밋 이력을 별도로 스캔했습니다.

  • 실 자격증명·PII: 전체 이력에서 0건. DB 비밀번호·RSA 키 등은 전부 학습용 dev 값이며 실서비스 자격증명이 아니다.
  • .secrets/·.env 커밋 이력: 0건. 둘 다 처음부터 .gitignore 대상이었고, 이력을 뒤져도 실수로 커밋된 적이 없다.
  • 커밋 author/committer 이메일의 오타(gamil.com)를 git filter-repo --mailmap으로 정정 — 이건 민감정보가 아니라 기여 그래프 연결(GitHub이 커밋을 계정에 매칭) 목적의 이력 재작성이었다(→ PHASE-COMMIT-MAP.md 상단 경고 참고).

교훈: "비밀이 커밋되면 리라이트가 아니라 로테이션." 이번 재작성은 민감정보 제거가 목적이 아니었지만, 만약 그랬다면 git filter-repo로 이력에서 지우는 것만으로는 부족하다 — 그 커밋을 참조하는 포크·클론·이미 받아 간 git fetch가 있다면 "고아 커밋"은 GitHub 서버 쪽에도 한동안 남는다(reflog·GC 유예기간). 유출된 비밀의 유일하게 확실한 대응은 **그 비밀 자체를 무효화(로테이션)**하는 것이다 — 이력 재작성은 위생 조치일 뿐, 보안 조치가 아니다.

5. API 변화 요지

이번 감사로 바뀐 외부 API 동작(§2 IDOR 항목의 결과):

  • POST /orders의 customerId 몸통 필드는 이제 무시된다. 실제 고객 id는 항상 JWT subject에서 유도된다 (CustomerIds.fromSubject). 요청 본문에 customerId를 넣어도 무해하게 무시되므로 기존 클라이언트/스크립트는 그대로 동작한다(하위 호환 유지) — 다만 그 값이 더 이상 신뢰되지 않는다는 점은 통합 대상이라면 알아 둬야 한다.
  • GET /orders/{id}가 403을 반환할 수 있다. 요청자가 그 주문의 소유자가 아니고 ADMIN도 아니면 AccessDeniedException → 403. 이전에는 인증만 됐으면 아무 주문이나 조회할 수 있었다.
  • 게이트웨이에서 /payments 라우트가 사라졌다. POST :8000/payments(또는 /payments/**)는 더 이상 게이트웨이를 통해 도달할 수 없다(404 또는 라우트 없음). 결제는 오직 Saga(Kafka 커맨드)로만 일어난다. payment-service를 클러스터/컴포즈 내부에서 직접 호출하는 것은 여전히 가능하지만(그 경로엔 자체 JWT 검증이 있다), 공개 게이트웨이로는 노출되지 않는다.
